## G-1 · The bundle fetch, if it happens at all, is a 64 KB range request

*Largely superseded by **G-2**, which removes the bundle from the normal path
entirely. Kept because the bundle walk should survive as a fallback, and this is
how to make that fallback cheap.*

`soundcloud-client-id.ts` documents the cold path as *"the homepage takes ~1.9 s
and the asset bundle holding the id another ~3.2 s, so a cold resolve costs about
five seconds"*, and builds the deadline-and-abstain design on that number.

**The bundle does not have to be downloaded.** Measured against
`55-121aab84.js`, the bundle the last-first walk lands on:

```
client_id at byte offset 2 860  of  2 971 671   (0.1% in)
a-v2.sndcdn.com sends  Accept-Ranges: bytes

  full GET                200   2 902 KB   2 950 ms
  full GET + gzip         200     802 KB   2 153 ms
  Range: bytes=0-65535    206      64 KB   1 548 ms
  Range: bytes=0-32767    206      32 KB   1 355 ms
  Range: bytes=0-16383    206      16 KB   1 378 ms
  Range: bytes=0-8191     206       8 KB   1 641 ms
```

Every range recovered `QUUtl3ZAhuSPgQmsJHdB7KXkYMKsPLXk`, the same id the full
download yields. Below 64 KB the time is handshake and round trip, not bytes —
so take the headroom for free and ask for 64 KB.

**There is exactly one `client_id` in the bundle.** All 2.9 MB were scanned:
one occurrence, at 2 860. No decoys, so a prefix read cannot pick up the wrong
one. The reverse-scan folklore inherited from yt-dlp is about *which bundle*,
not which occurrence, and the last-first walk in `fetchClientId` already handles
that correctly — it found the id in bundle 8 of 9, and bundles 0–7 hold none.

**What it does to the design.** On the bundle path, cold resolve goes from ~5 s
to **~1.4 s + ~1.4 s ≈ 2.8 s** — still over the 2 500 ms deadline, so
abstain-on-first-search would stay correct *if this were the normal path*. G-2
shows it need not be. The single-flight cache matters either way.

**The change is two lines** in `text()` — an optional `Range` header, and
accepting `206` alongside `ok`. Note `response.ok` is already true for 206, so
only the header is strictly needed.

**One caveat.** Offset 2 860 is where it sits in today's bundle, not a
guarantee. A 64 KB prefix is 23× the observed offset; if a deploy ever moves it
past that, the miss is silent — the resolver returns `null` and SoundCloud
abstains for four hours. Worth one fallback to the full fetch when the prefix
misses, which costs nothing in the normal case.

## G-2 · The id **is** in the homepage — so the bundle fetch is unnecessary entirely

**This entry first claimed the opposite, and was wrong. Retracted and replaced.**
The first pass searched the homepage for `client_id:"…"`, `clientId` and
`client_id=` and found none, and concluded `BLOCKED.md` was mistaken to say
cobalt and soundcloak read the id from the hydration blob. That conclusion was an
artefact of guessing the key name. `BLOCKED.md` was right.

Reading soundcloak's `lib/sc/init.go` gives the actual shape it looks for:

```go
var hydrationClientIdRegex = regexp2.MustCompile(
  `{"hydratable":"apiClient","data":{"id":"([A-Za-z0-9]{32})"`, regexp2.None)
...
// fallback to searching inside JS scripts, inspired by cobalt
```

The id is not stored under a key called `client_id` at all. It is the `id` field
of an `apiClient` hydratable. Applying that regex to the live homepage:

```
GET https://soundcloud.com          67 300 B in 1 627 ms
{"hydratable":"apiClient","data":{"id":"QUUtl3ZAhuSPgQmsJHdB7KXkYMKsPLXk","isExpiring":false}}
                                    ^ identical to the id in bundle 55
```

**Verified end to end, twice.** The id taken from the hydration blob was used
directly against api-v2 with no other step: `policy=MONETIZE`,
`duration=233759`, `monetization_model=AD_SUPPORTED` on Ed Sheeran's *Shape of
You*, and a `3/100` SNIP rate across five queries — identical to the first
sample taken an hour earlier from the bundle-extracted id. Same id, same
entitlement, one request instead of two.

**One request. No bundle.** The seven hydratables present are `anonymousId`,
`apiClient`, `features`, `geoip`, `privacySettings`,
`statsigClientInitializeResponse` and `trackingBrowserTabId`.

### What this does to the cold path

```
today          homepage 1.4 s  +  full bundle 2.9 s   ≈ 4.3–5 s
with G-1       homepage 1.4 s  +  64 KB range 1.4 s   ≈ 2.8 s
with G-2       homepage 1.6 s                          ≈ 1.6 s
```

**~1.6 s is inside the 2 500 ms deadline**, so the abstain-on-first-search path
would stop firing in the normal case rather than always firing. That is a
different product behaviour, not just a faster one: the first search on a cold
instance would include SoundCloud instead of silently omitting it.

### The shape, and why the existing tests survive it

```ts
/** The `client_id` SoundCloud hydrates the page with, if it is there. */
const HYDRATION_PATTERN =
  /\{"hydratable":"apiClient","data":\{"id":"([A-Za-z0-9]{32})"/;

export function clientIdFromHydration(html: string): string | null {
  return HYDRATION_PATTERN.exec(html)?.[1] ?? null;
}

// in fetchClientId, before the bundle walk:
const home = await text("https://soundcloud.com", userAgent, signal);
if (!home) return null;
const hydrated = clientIdFromHydration(home);
if (hydrated) return hydrated;
// … existing last-first bundle walk, now the fallback
```

**Run in Node with the exact user-agent `providers.ts` uses and the regex exactly
as written above: `1 423 ms`, one request, and the id authenticates against
api-v2 with `policy=MONETIZE`.** Not a sketch — this is the measured path.

**`soundcloud-client-id.test.ts` keeps passing unchanged**, and gets better for
free: its stubbed homepage (`BUNDLES`) carries no hydration blob, so every
existing test now exercises the *fallback* path rather than the only path. That
is the coverage you want — the fast path is trivial to test on its own, and the
fallback is the part that was previously untested in isolation.

**G-1 is not wasted — it becomes the fallback's fallback.** soundcloak keeps the
bundle walk precisely because the hydration blob is not guaranteed, and
`soundcloud-client-id.ts` should keep it too. The ladder is: hydration blob →
ranged bundle prefix → full bundle. Only the first is on the normal path.

**Two more things from the same line.** `isExpiring: false` sits next to the id —
a freshness signal nothing else exposes, and worth reading rather than relying
solely on a four-hour TTL. And soundcloak's regex is `{32}` exactly where
`CLIENT_ID_PATTERN` in this repo is `{20,}`; every id observed here has been
exactly 32 characters.

**Also confirmed from the same file, closing G-3a:** `cfg.AccountTokens` sets an
`Authorization` header on outgoing api-v2 requests, rotating through a configured
list. That is the `UseTokensInAPI` mechanism, and it is what
`SOUNDCLOUD-PROXIES.md` suspected. It explains `sc.monochrome.tf` and
`soundcloak.tijn.dev` — but **not** the anonymous direct route, which carries no
token and still sees the full catalogue. So the doc's mechanism is real and its
conclusion still does not follow: a token is one way to get the licensed
catalogue, not the only way.

## G-3 · The instance trade-off in `SOUNDCLOUD-PROXIES.md` is not the one described

That document's closing argument is a choice between two bad options:

> - **maid.zone** — anonymous, no one's account involved, but 10–18% of results
>   arrive as 30-second previews […]
> - **sc.monochrome.tf** — correct durations, because your listeners' searches
>   ride on a stranger's SoundCloud account, through Cloudflare.
>
> Neither is a good answer for a deployment other people use.

It attributes the correct durations to `UseTokensInAPI` attaching the operator's
account. **Measured same-minute, that does not hold.**

```
Ed Sheeran — Shape of You, limit=20, all within one minute

source                 duration   full_duration    policy   SNIP/20  isrc/20    ms
sc1.maid.zone             30000          233744      SNIP         1        5   1706
sc3.maid.zone             30000          233744      SNIP         1        5   2094
sc.monochrome.tf         233759          233744  MONETIZE         0        5   2229
soundcloak.tijn.dev      233759          233744  MONETIZE         0        5   1537
direct api-v2 (anon)     233759          233744  MONETIZE         —        —      —
```

Two facts break the framing:

- **`soundcloak.tijn.dev` returns the full duration too**, and the same document
  ranks it as the fastest instance with the *lowest* preview rate (4%). It is not
  the Cloudflare one and there is no reason to think it is the account one.
- **A fresh anonymous guest `client_id`, no account of any kind, returns
  `233759 / MONETIZE`** — the identical number. So an operator's token is *not*
  what lifts the preview gate, because the gate is not there to lift when the id
  is fresh.

**Sampled three times across the session, identical every time**, and
`media.transcodings[].snipped` tracks `policy` exactly — `{True}` on both
maid.zone instances, `{False}` on the direct route, `soundcloak.tijn.dev` and
`sc.monochrome.tf`. This is the session's load-bearing claim and it is the most
re-measured thing in the file.

`/_/info` does not expose `UseTokensInAPI` at all — it reports only
`ProxyImages`, `ProxyStreams` and `EnableAPI`, identically on the instances that
disagree. So the attribution in the doc is inference from a setting that cannot
be observed from outside, and the simpler explanation fits every row: **the
maid.zone instances are serving a stale or degraded `client_id`.**

### The merge damage is already fixed — and that makes the instance choice matter *more*

*Superseded within the hour by `aa5a5ca`, and corrected here rather than left
standing.* This entry originally recommended reading `full_duration ?? duration`
so a SNIP track would merge instead of double-listing. `soundcloud.ts` now does
something stronger and better argued: `if (raw.policy === "SNIP") return null`,
dropping them, because this provider's `playback` is `queue` and a queue member
that stops at 0:30 breaks that promise. The `full_duration` observation stands —
it is `233744` on every row above, including both SNIP ones — but it is no longer
the fix.

**Dropping inverts the consequence of the instance table.** A SNIP result is no
longer a bad row; it is a *missing* row. So the preview rate is now a measure of
how much catalogue an instance throws away:

```
maid.zone sc1/sc3    15–18% of results discarded
sc.monochrome.tf      8%
soundcloak.tijn.dev   4%
direct api-v2 (anon)  3%     (3/100 over five queries)
```

Same query, same minute — so this is not catalogue variance, it is the credential
the search runs under. **Choosing `sc1.maid.zone` now costs roughly one result in
six**, silently. That is a stronger argument for the direct route than anything in
`BLOCKED.md`'s update, and it was not visible while SNIP rows were being listed.

### G-3a · What the disagreement actually is, isolated

*Added after the entry above, chasing the cause rather than the symptom.*

Asking every instance for **the same track id** — `301161123`, Ed Sheeran's own
upload of *Shape of You* — removes catalogue variance from the question:

```
direct api-v2 (anon)   policy=MONETIZE   duration=233759   monetization=AD_SUPPORTED
soundcloak.tijn.dev    policy=MONETIZE   duration=233759   monetization=AD_SUPPORTED
sc.monochrome.tf       policy=MONETIZE   duration=233759   monetization=AD_SUPPORTED
sc1.maid.zone          policy=SNIP       duration= 30000   monetization=NOT_APPLICABLE
sc2.maid.zone          policy=SNIP       duration= 30000   monetization=NOT_APPLICABLE
sc3.maid.zone          policy=SNIP       duration= 30000   monetization=NOT_APPLICABLE
```

`monetization_model` is the field that was missing from the picture:
`AD_SUPPORTED` against `NOT_APPLICABLE`. Four candidate causes were ruled out:

- **Not geography.** The three maid.zone instances are DE, US and JP and all
  three say `SNIP`; `soundcloak.tijn.dev` is also DE and says `MONETIZE`.
- **Not the User-Agent.** The same request with `curl/8.0` returns `MONETIZE`.
- **Not an expired credential.** A garbage `client_id` answers `401`, so
  maid.zone's authenticates — it is valid, just not entitled.
- **Not the query.** Passing a fresh `client_id` to a maid.zone instance changes
  nothing; soundcloak replaces it with its own, as its docs say.

**And it is not the coverage figure the table implies.** Taking the tracks direct
api-v2 marks `AD_SUPPORTED` and asking `sc1.maid.zone` about each:

```
official Ed Sheeran uploads gated by maid.zone   11 / 12
non-monetized re-uploads and remixes (control)    0 / 5
```

So maid.zone does not lose a random 15–18%. **It loses very nearly the entire
officially-licensed catalogue**, and keeps the remixes and re-uploads. The
15–18% in the instance table is simply how much of an average result page is
label content. Corrected against my own framing above: it is not one result in
six, it is *Ed Sheeran's own uploads, all of them*.

Since `aa5a5ca` drops SNIP rather than listing it, that is now a silent hole. On
a maid.zone base, searching `Ed Sheeran` returns remixes and covers and no Ed
Sheeran.

**And it is not a tracked upstream bug, so do not wait for a fix.** soundcloak's
issue tracker has seven issues in its life, one open (`#7`, about download
links). Nothing mentions preview gating, `policy`, or account tokens. The
instances that show it are simply run without `AccountTokens` configured; that
is a deployment choice by each operator, not a defect anyone is working on.
**Instance choice is the operator's problem permanently**, which is one more
argument for the direct route over pointing at a stranger's box.

### G-3b · A datacenter IP is not gated — measured by accident

**The measurements above were made from a datacenter VPN address**, not a
residential one: `195.177.93.16`, **AS212238 Datacamp Limited**, Zürich. That was
not deliberate; it was noticed while chasing G-3a.

It makes the result stronger rather than weaker. `BLOCKED.md` warns that "a VPN
changes YouTube's behaviour" and that datacenter ranges are blocked there, and it
would be natural to assume SoundCloud does the same. **It does not** — a
datacenter IP in Switzerland, with a freshly-extracted guest `client_id`, sees
the full ad-supported catalogue while three self-hosted instances do not. That is
direct evidence that `SOUNDCLOUD_DIRECT_API` would keep working from a serverless
function's egress, which is the obvious worry about shipping it.

**One VPN endpoint is not a survey**, and Vercel's ranges were not tested. But it
inverts the burden of proof: the failure mode to worry about is the credential,
not the address.

**Two things this means for the repo, and one warning.** The direct route is not
merely the more convenient hatch — it is the only one measured here that reliably
sees licensed releases, which is a stronger argument than the hosting one
`BLOCKED.md` currently makes. And the widget path is worth knowing about
separately: `w.soundcloud.com/player/` loads **DataDome** bot protection
(`window.ddjskey`) and talks to `api-widget.soundcloud.com` rather than `api-v2`.
Embedding it in a real browser is fine — that is what DataDome expects — but
nothing should ever try to drive that host from a server.

**The warning:** a VPN is active on this machine right now. `BLOCKED.md` already
says to check for one before trusting a measurement, and that applies to
measurements taken *here*, including several in this file and possibly in others.

### Still unresolved

The Widget question from yesterday is narrowed but not closed. Asking
`api-widget.soundcloud.com` — the host the Widget itself uses — for the same
track with a web `client_id` returns `MONETIZE`, so the Widget's host is not a
lower entitlement tier. What a *real embedded Widget* does with a track that some
other credential calls `SNIP` still needs a browser.

What else survives:

- **A SNIP track still plays 30 seconds and stops.** Reading `full_duration`
  fixes identity, not playability, and `BLOCKED.md` is right that a queue member
  which stops at 0:30 is broken rather than degraded. It needs the badge or the
  filter regardless.
- **Open question worth testing on a phone or a browser:** the SNIP policy is
  what the *search credential* is allowed to see. Playback goes through the HTML5
  Widget, which authenticates as the visitor's own browser. Whether a track
  flagged `SNIP` in search plays in full in the Widget for a signed-in listener —
  or for anyone — is not established, and the answer decides whether SNIP is a
  filter or only a badge. Nothing in this repo currently claims to know.

## G-4 · Direct api-v2, measured on the same axes as the instance table

So the row can go in the table. Anonymous guest `client_id`, five queries,
100 tracks parsed:

```
30s-gated (SNIP or >5s duration divergence)     3 / 100    3%
ISRC present                                   45 / 100   45%
search latency                       2 370 – 2 859 ms, median 2 567 ms
```

Against the proxies: **the preview rate is the best measured** (3% against

The richer ISRC rate is worth more than it looks. `SUGGESTIONS.md` S-8 records
that Audius has none and the merger falls through to title+artist+duration with
nothing to backstop it. At 45%, SoundCloud via the direct route is the best merge

## G-5 · `filter="songs"` is not "essentially exclusively" ATV. It is exclusively ATV — and two tiers are unhandled

`BUGS.md` B-2 blames the fall-through failure on `filter="songs"` returning art
tracks "essentially exclusively". Re-measured independently through
`youtubei.js`, using the same InnerTube params `ytmusicapi` sends, over ten
queries × two filters:

```
type                     songs   videos    share   in the 4-way rank?
ATV                        600        0    50.4%   yes
UGC                          0      507    42.6%   yes
OMV                          0       72     6.1%   yes
OFFICIAL_SOURCE_MUSIC        0        6     0.5%   NO — falls to "unknown"
PODCAST_EPISODE              0        5     0.4%   NO — falls to "unknown"
```

**`filter="songs"` returned ATV 600 times out of 600, and nothing else.** The two
filters are perfectly disjoint by type — `videos` returned no ATV at all. B-2's
diagnosis was right and its hedge was unnecessary: this is not a tendency, it is
the definition of the filter. Worth strengthening the wording, because the hedge
invites someone to re-litigate whether the supplementary `videos` search is
really needed.

**Two tiers exist that `models.py`'s rank has no branch for**, and this applies to
the Python sidecar as it stands today, independently of anything in F-2:

- **`PODCAST_EPISODE`** falls to `unknown` (rank 2), which places it *above* every
  art track. A podcast episode is not a degraded song, it is not a song — the
  right treatment is probably a filter, not a rank.
- **`OFFICIAL_SOURCE_MUSIC`** also falls to `unknown` (rank 2), which is likely
  too low: the name and its company in the results suggest an official-video
  class that belongs beside `OMV` (rank 0), and `OMV` is the tier B-3 measured as
  **never barred from embedding**.

### Re-measured later the same day: this is not long-tail, and it cuts a suggested search

That was an artefact of the query set. Broadened to twelve queries under

```
OFFICIAL_SOURCE_MUSIC    30      <- unhandled
PODCAST_EPISODE          12      <- unhandled
SHOULDER                  3      <- unhandled, a fifth tier
```

**`OFFICIAL_SOURCE_MUSIC` is 30 against OMV's 141** — better than one in five of

**These are official artist-channel uploads.** They belong with `OMV`, not below
`UGC`.

**What the current rank does to `Fred again Delilah`** — the query the player
itself fires on fall-through, and `Fred again..` is in `SUGGESTED_SEARCHES`:

```
20 candidates:  OMV=4   OFFICIAL_SOURCE_MUSIC=2   UGC=14

Fred again..'s own upload of the exact song (2_64XAqYgJ0, 9M views)
  position with _embed_rank as written        19 of 20

  survives limit=10 (what the player asks for)   NO
```

**The artist's own recording is truncated out of the candidate list**, while ten

`PODCAST_EPISODE` goes the other way. All twelve came from `lofi study mix`, and

(`OMV 1.15 · UGC 1.0 · ATV 0.8`, unknown 0.95) scores recommendations. Both were
written from the same three-tier picture and both are wrong in the same
direction.

## G-6 · Mixcloud, the two details a provider needs

Following up F-3 with the questions an implementation actually hits.

**Paste support works, but only server-side.** `app.mixcloud.com/oembed/` answers
`200` for a cloudcast URL with title and author — so `resolveUrl` can accept a
pasted Mixcloud link. It sends **no** `Access-Control-Allow-Origin`.

**Search is browser-callable, and it reflects any origin.** Tested across four
origins and two paths, all eight combinations echoed the origin back:

```
Origin: https://timbre.vercel.app  → access-control-allow-origin: https://timbre.vercel.app
Origin: https://example.com        → access-control-allow-origin: https://example.com
Origin: http://127.0.0.1:3000      → access-control-allow-origin: http://127.0.0.1:3000
```

So the split is exactly the one `BLOCKED.md` already records for soundcloak,
where the `v2` proxy sets the header and `/_/searchSuggestions` does not:
**search from the visitor's browser, resolve a pasted URL from the server.**

Note it *reflects* rather than sending `*`, alongside
`access-control-allow-credentials: true`. A default `fetch()` omits credentials
so this is fine, but do not add `credentials: "include"` to it.

**No throttling observed.** Ten rapid distinct searches: `200` ×10, latency
892–1 432 ms, no `Retry-After` on any.

**Apple Music's embed was checked and is weaker than Spotify's.** F-1 produced
Apple Music track ids at 9/15, so the obvious follow-up is whether they can be
rendered. `embed.music.apple.com/us/song/{id}` answers `200` with **no**
`X-Frame-Options` and no `frame-ancestors`, so it does embed — but the page is
**2 187 bytes of MusicKit loader** and contains no title, no artist, no preview
URL and no `postMessage` surface. Everything is drawn client-side by MusicKit JS.

That is the opposite of Spotify's embed, which server-renders title, artists,
duration and `isPlayable` — the thing the Spotify provider reads. So Apple's ids
buy a frame that plays a 30-second preview for non-subscribers and nothing that
can be scraped or scripted. **Not worth a panel**, and worth recording so the
9/15 does not look like an unexploited win.

## G-7 · The new `RETRY_AFTER_MS` guards a failure mode that was not the one observed

*Written against `soundcloud-client-id.ts` as it stands after the crawl-budget
and retry-backoff changes. The backoff is right; only its stated reason is at
issue.*

The comment on `RETRY_AFTER_MS` says:

> The likeliest failure here is precisely the one that must not be retried in a
> loop — **a datacentre IP being refused, which is the normal answer for a free
> serverless host**

Three measurements from today point the other way:

- **A datacenter IP was not refused.** Every crawl and every api-v2 call in this
  file was made from `195.177.93.16`, AS212238 Datacamp — a datacenter network,
  not a residential one. The homepage answered `200`, the ranged bundle answered
  `206`, and api-v2 answered `200` with full `AD_SUPPORTED` entitlement,
  repeatedly, over about half an hour.
- **Three more datacenter hosts resolve ids successfully right now.** The
  `sc1`/`sc2`/`sc3.maid.zone` instances are VPSes in DE, US and JP. All three
  hold a *valid* `client_id` — a garbage one answers `401` and theirs does not —
  and all three serve api-v2 results. If SoundCloud refused datacenter ranges
  the crawl, those instances could not function at all.
- **The failure that does occur is invisible, and backoff cannot help it.** What
  distinguishes those hosts is not refusal but **entitlement**: their credential
  returns `policy: "SNIP"` for the licensed catalogue (G-3a). That is a `200`, so
  nothing retries, nothing logs, and since `aa5a5ca` those rows are dropped —
  the operator sees a working SoundCloud source with no Ed Sheeran in it.

**Keep the backoff.** A five-minute cooldown on a failed ten-request crawl is
good defensive design whatever the cause, and `CRAWL_BUDGET_MS` fixing the
never-settling `inFlight` is a real bug fix. The note is only that the premise is
reasoned rather than measured, and the evidence available leans against it — so
it should read as an assumption in `SUGGESTIONS.md` terms, not a fact.

**What would actually be worth building instead**, given the failure mode that
was observed: a cheap entitlement self-check after a resolve. Ask api-v2 for one
known-`AD_SUPPORTED` track id and look at `policy`. If it comes back `SNIP`, the
credential is the degraded kind and the operator should be told, because the
alternative is silent partial catalogue. That is one request per four-hour TTL.

## G-8 · The `/api/spotify` route's reason for being server-side is wrong — and the real MusicBrainz rules are different again

The new route says:

> **Server-side because MusicBrainz makes it so.** The ListenBrainz labs host
> sends `Access-Control-Allow-Origin: *` and would be reachable from the browser,
> but the ISRC hop runs through MusicBrainz, **which sends no CORS header** and
> requires a contactable `User-Agent` that script cannot set.

**MusicBrainz does send the header.** Measured today, case-insensitively:

```
GET  /ws/2/isrc/AUFF01500784?fmt=json      Origin: https://timbre.vercel.app
  200 · Access-Control-Allow-Origin: *
        X-RateLimit-Limit: 1200 · X-RateLimit-Remaining: 752

OPTIONS  (preflight, same URL)
  200 · Access-Control-Allow-Origin: *
        Access-Control-Allow-Methods: GET, OPTIONS
        Access-Control-Allow-Headers: Authorization, Content-Type, User-Agent
```

`BLOCKED.md` already records this correctly — *"It also sends
`Access-Control-Allow-Origin: *` and `X-RateLimit-Limit: 1200`"* — so the two
documents now disagree and `BLOCKED.md` is the one that is right. MusicBrainz
even names `User-Agent` in its preflight allowlist, which is a service expecting
browser callers.

### And the User-Agent rule is not the one either document states

`BLOCKED.md` says *"MusicBrainz `403`s a generic User-Agent … send a descriptive
one and the same request answers `200`."* That is not what happens. Same URL,
varying only the header:

```
(no User-Agent header)                    403
User-Agent:                    (empty)    403
Mozilla/5.0                               403
curl/8.0.1                                200
Python-urllib/3.14                        200
python-requests/2.31                      200
Timbre/0.1 ( https://example.com )        200
Mozilla/5.0 (Windows NT 10.0 …) Chrome/126 …   200
```

**What is blocked is the absent, the empty, and the bare `Mozilla/5.0`** — the
half-hearted browser impersonation. Ordinary tool user-agents pass. `curl` is not
403'd, and the current wording implies it is, which would send the next person
chasing a header that was never the problem. Re-checked across
`/ws/2/isrc/…`, `/ws/2/recording?query=…` and `/ws/2/artist/…`: `200` on all
three for every tool UA.

**So the chain is browser-callable after all.** A real browser sends a full
Chrome user-agent, which answers `200`; MusicBrainz sends `ACAO: *`; the labs
host sends `ACAO: *` with a `21600`-second preflight cache. The only hop that
cannot move is Deezer, which sends no CORS header — but **the ISRC is already in
the client**, on any song Deezer merged into. For those songs `/api/spotify`
could be two `fetch` calls from the visitor's browser: no server round trip, no
per-instance `hits` map, and MusicBrainz's 1 200/hour budget spent per *visitor*
rather than pooled on one egress IP. That last point is the same argument
`BLOCKED.md` makes about Audius and iTunes, and it applies here with more force
because the budget is published.

The server route is still needed for songs with no ISRC. This is an addition, not
a replacement.

### The load-shedding is the real hazard, and it is worse than the labs host

Ten rapid calls to the same MusicBrainz URL with a valid UA:

```
sample 1 (tight curl loop)   503 200 503 200 200 200 503 200 200 200   3/10 failed
sample 2 (~20 min later)     200 ×10                                   0/10 failed
ListenBrainz labs, same test 200 ×10                                   0/10 failed
```

**Intermittent, not a rate.** The first sample is the honest warning and the
second is why it must not be quoted as "30%": load-shedding happened under one
tight burst and not under a looser one twenty minutes later. What is established
is that MusicBrainz *does* shed under concurrency and the labs host did not, in
either sample — which is the opposite of the route comment's implied ordering,
where the labs host is the un-SLA'd one. The route's decision to cache hits and never cache abstentions is therefore
not merely prudent — it is load-bearing, and the comment currently justifies it
only by the labs host being un-SLA'd. On the evidence here MusicBrainz is
the flakier of the two under concurrency. Worth widening that comment, and worth
a retry on `503` specifically, which is a different thing from a `404` — the
first means "ask again", the second means "not there".

## G-10 · E-18's remedy exists, and it costs something the route already decided against

`EXPOSURE.md` **E-18** is open on every reader's lyrics lookup arriving at LRCLIB
as one client. The obvious fix is to call it from the browser, and LRCLIB permits
that:

```
GET lrclib.net/api/search?q=…    200 · Access-Control-Allow-Origin: *
                                       Access-Control-Expose-Headers: retry-after
```

`ACAO: *` with or without an `Origin` header, and — the interesting part — it
**exposes `Retry-After` to script**. A server does not need that header exposed;
only a browser client does. LRCLIB is explicitly accommodating browser callers
and telling them how to back off.

**But `app/api/lyrics/route.ts` already considered this and chose otherwise**,
for three stated reasons: it keeps the reader's IP away from a third party, it
makes the response cacheable (`revalidate = 86_400`), and it survives a blocker
filtering the upstream host. Those are all real, and the first is the same
privacy posture the whole product is built on.

So E-18 is not an oversight, it is a **trade-off already made** — and it should be
recorded in `EXPOSURE.md` as one rather than as an open question, because the
remedy is known and was declined. What is genuinely open is narrower: the route
makes three `fetch` calls and **handles no `429` and reads no `Retry-After`**,
which is the thing E-18 is actually about. Honouring the header LRCLIB goes out
of its way to expose is the fix that does not cost the reader's IP.

## G-12 · The desktop User-Agent in `providers.ts` is load-bearing and says nothing about it

`clientIdResolver()` hardcodes a Chrome 140 desktop user-agent. That is the right

## G-15 · A real browser, driving the IFrame API — and why its numbers must not be used

Playwright with the system Chrome is available on this machine, so B-2's method —
*"measured over 64 uploads across 15 chart songs, in a real browser driving the
IFrame API"* — is reproducible here. It was reproduced, and **the numbers it
produces on this machine are worthless.** Recorded because the *reasons* are
worth having, and two of them are traps.

### Trap 1 — resolving on the first player event records a false "plays"

The first harness treated `CUED`/`BUFFERING`/`PLAYING` as success and resolved on
the first event. Result: **48 of 48 "plays", including 14 art tracks**, against
B-2's measured 6.7% barred. `loadVideoById` cues immediately and **error `150`
arrives afterwards**, so the harness recorded the outcome before the failure
existed.

The fix is to collect every event for a fixed window and judge at the end, and to
count only state `1` (`PLAYING`) as success — `CUED` is not evidence a video can
play. Anyone re-running B-2's measurement will hit this, and it fails in the
reassuring direction.

### Trap 2 — the VPN puts you in another country, and that is what the bars are

With the corrected harness the numbers inverted absurdly:

```
tier                     n   barred   rate      B-2's residential measurement
ATV                     14       14   100%      6.7%
OMV                     10        9    90%      0%
OFFICIAL_SOURCE_MUSIC   12        5    42%      —
UGC                      8        5    63%      —
PODCAST_EPISODE          4        4   100%      —
```

**Not headless detection** — a headed Chrome with a real window returns
byte-identical verdicts. **Not a blanket block** either, which is the useful part:

```
Me at the zoo         (2005, independent)      plays
Big Buck Bunny        (Creative Commons)       plays
YouTube's own API demo                         plays
Never Gonna Give You Up (Sony/RCA)             BARRED 150
Fred again.. — Delilah, art track (label)      BARRED 150
Fred again.. — Delilah, artist upload          plays
```

Three of four controls play. What is barred is **label-owned content**, and
`youtubei.js` reports the assigned region as **`CH`** — the VPN's exit is Zürich.
So these are per-territory embed restrictions on rights-managed catalogue, not a
datacenter-IP reputation ban.

### What this is actually worth

**It gives `BLOCKED.md`'s VPN warning a mechanism and a signature.** That entry
says "a VPN changes YouTube's behaviour… if playback goes flaky, check whether a
VPN is active before assuming a code bug." True, and now specific:

> With a VPN on, **chart songs fail and indie uploads play**. Every candidate in
> the fall-through ladder is label content, so the ladder exhausts and the player
> reports *"Every copy of this song blocks playback outside YouTube."* That is
> **B-6's exact string**, produced by the network rather than by a bug — and B-6
> is on record as having cost a long investigation for precisely this reason:
> a confident sentence asserting a cause nobody verified.

The recognisable signature is the split. A real embed problem does not
politely spare Creative Commons uploads.

**It also confirms the `NOT-A-BUG` note a third way.** Asking InnerTube directly
via `getBasicInfo(id, 'WEB_EMBEDDED')` returns
`status=UNPLAYABLE, reason="Video unavailable"` for **all four controls —
including the three that then played in a real iframe**. The existing note rests
on oEmbed answering `200` and `playableInEmbed: true` for barred uploads; this is
a third independent server-side method, and it fails in the *opposite* direction.
Server-side embeddability determination is not merely unreliable, it is wrong in
both directions.

### What it does not settle, and what would

**G-5's ranking fix cannot be justified by bar rates measured here.** The
`OFFICIAL_SOURCE_MUSIC` figure of 42% is a Swiss-territory artefact sitting
between OMV's 90% and UGC's 63%, and it says nothing about the tier.

The case for ranking `OFFICIAL_SOURCE_MUSIC` with `OMV` rests on **what the tier
is** — sampled and verified as official artist-channel uploads
(*Delilah (Pull Me Out of This)*, 9M views, Fred again..'s own channel;
*Fred again..: Tiny Desk Concert*, 16M) — not on embeddability numbers.

**The harness works and takes about ten minutes to run.** With the VPN off it
would produce the real per-tier table, settle `OFFICIAL_SOURCE_MUSIC` and
`PODCAST_EPISODE` properly, and re-validate B-2's own figures two months on. It
is four small files and is not in the repo; say the word and it can go in
`scripts/`.

## G-16 · Making Timbre VPN-friendly — measured from inside a VPN

The question is a good one and the answer is narrower than it sounds, because
**only one source breaks.**

### What a VPN actually does, measured from a CH exit

Every non-YouTube source is untouched:

```
Audius  /v1/tracks/{id}/stream   206  audio/mpeg          plays
Deezer  cdnt-preview 30s          206  audio/mpeg          plays
iTunes  previewUrl 30s            206  audio/x-m4p         plays
SoundCloud  widget getCurrentSound   policy=MONETIZE
                                      duration=233759 (full)  streamable=true
```

That last one is worth pausing on: the **SoundCloud Widget** — Timbre's actual
playback path — reports Ed Sheeran's *Shape of You* as full-length and
`MONETIZE` from this VPN. SoundCloud does not appear to apply a territorial
embed gate at all.

**YouTube does, and it is severe.** Walking the real fall-through ladders —
the sidecar's own ranking, truncated to the `limit=10` the player requests, each
candidate driven through the IFrame API in Chrome:

```
song                          walked  outcome
Blinding Lights The Weeknd        10  ALL 10 BARRED
As It Was Harry Styles            10  ALL 10 BARRED
Wonderwall Oasis                  10  ALL 10 BARRED
Shape of You Ed Sheeran           10  ALL 10 BARRED
Rolling in the Deep Adele         10  ALL 10 BARRED
Smooth Operator Sade              10  ALL 10 BARRED
Get Lucky Daft Punk                3  plays on #3 (OMV)
Delilah Fred again                 4  plays on #4 (UGC)
Archangel Burial                   1  plays on #1 (UGC)
360 Charli xcx                     8  plays on #8 (UGC)
Xtal Aphex Twin                    8  plays on #8 (UGC)
Glue Bicep                         7  plays on #7 (UGC)

every copy barred: 6/12          (B-4's residential figure: 0/15)
walked when it worked: mean 5.2 candidates
```

**Half the songs are completely unplayable through YouTube, and it is exactly the
mainstream half.** B-4 was closed on the reasoning that "0 of 15 songs had every
candidate barred, so this is genuinely long-tail". That is true on a residential
connection and false on a VPN — the same measurement gives 6 of 12.

### What "VPN-friendly" cannot mean

It cannot mean getting those six to play on YouTube. Territorial embed
restriction is rights enforcement, and routing around it is the same class of
thing `BLOCKED.md` declines elsewhere. **The goal is not to defeat the block. It
is to stop the block being fatal, and to stop the app lying about it.**

### Four changes, in order of value

**1 · Make the fall-through cross-source. This is the VPN fix.**
`player-context.tsx` still has `youtubeIdOf()`, which walks only `ytmusic`
candidates — so when the territory bars the catalogue, the entire ladder is one
rights regime and exhausts together. B-4 already named the remedy (*"other-source
ladder"*) and closed it as long-tail. **Under a VPN it is not long-tail, it is
half the catalogue.** The ladder should end by changing source, not by giving up:
SoundCloud widget (verified unaffected) → Audius → the 30-second preview.

All six barred songs have a working preview from *both* Deezer and iTunes under
this VPN (`206` on all twelve checks), so `57af890`'s preview fallback already
rescues every one of them — **as 30 seconds.** That is the honest floor. Full
playback for a chart song under a VPN needs SoundCloud, which needs the operator
to have enabled catalogue search.

**2 · Make the failure message true, with one control load.**
The current string asserts *"Every copy of this song blocks playback outside
YouTube"*. Under a VPN that is **false** — the copies are fine, the territory is
not — and asserting an unverified cause is precisely the mistake B-6 exists to
record. The signature is cheap to detect: **label content fails, independent
content plays.** Loading one known-embeddable control after the ladder exhausts
distinguishes the two:

```
control plays + every candidate barred  →  "This song isn't available to play in
                                            your region. If you're on a VPN, try
                                            turning it off."
control also barred                     →  a real player or network fault
every candidate barred, no control run  →  today's sentence, which may be wrong
```

Controls that survived from here: `jNQXAC9IVRw` (Me at the zoo),
`aqz-KE-bpKQ` (Big Buck Bunny), `M7lc1UVf-VE` (YouTube's own API demo). One load,
once per session, only on the exhausted path.

**3 · Demote YouTube for the rest of the session once the pattern shows.**
Mean 5.2 candidates walked even when it *works*, and each is a `loadVideoById`
plus a wait — so a VPN listener pays a long stall before every song. After the
ladder has exhausted twice in a session, stop leading with YouTube and let a
geo-neutral source go first. Cheap, reversible, and invisible to everyone else.

**4 · G-5 helps here too.** Under this VPN, `OFFICIAL_SOURCE_MUSIC` was barred
42% against OMV's 90%. Those rates are territory artefacts and must not be
quoted as tier properties (G-15) — but the *ordering* holds, and ranking that
tier properly puts more survivors into the ladder rather than truncating them out
of it.

### What this does not settle

Whether the six barred songs are barred **in every territory a VPN might exit
in**, or only in `CH`. One exit is one sample. The design above does not depend
on the answer — it depends only on the ladder being able to leave YouTube.

## G-17 · Letting the reader pick the source — what the badges can and cannot become

**Built. Verified in the running app** — see the end of this entry. Written as a
proposal and kept as one, because the reasoning is the part worth re-reading; the
facts it rests on were measured, the interface was a suggestion, and it is now
`apps/web/app/source-badges.tsx` plus a `prefer` argument on `play`/`load`.

### The machinery already exists; only the order is hardcoded

`player-context.tsx` `load()` already has a working attempt function per source —
`attempt` (YouTube), `attemptProgressive` (Audius, Archive), `attemptMixcloud`,
`attemptSoundCloud`, `attemptSpotify` — plus `setActiveSource` and the preview
rung. What it does not have is a way to say *which one*. The order is fixed:

```
youtubeIdOf → progressiveOf → mixcloudKeyOf → soundcloudUrlOf → spotifyIdOf → previewOf
```

So "let the reader choose" is not a new subsystem. It is **one optional argument
to `load()`** naming a preferred source, tried first, with the existing ladder
unchanged behind it as the fallback. Everything downstream already works.

### Only five of the eight sources can play, and the badges do not say so

```
queue   ytmusic · soundcloud · audius · mixcloud · archive    can be played and auto-advance
manual  spotify                                               embeds, cannot be script-started
link    deezer · apple                                        cannot embed — but both carry previewUrl
```

A row showing *SoundCloud · YT Music · Deezer · Apple* therefore has **two badges
that can play the song, and two that can only play thirty seconds of it.**
Rendering all four identically as "open on their site" hides that; rendering all
four identically as "play here" would be a lie of the same shape the SNIP drop
was added to avoid — this provider's `playback` is `queue`, which promises the
song.

Honest mapping, per badge:

| Badge | Click can mean |
| :--- | :--- |
| YT Music, SoundCloud, Audius, Mixcloud, Archive | **Play from here** — real queue member |
| Spotify | **Open the panel** — plays, but the queue rests until pressed |
| Deezer, Apple | **Play 30 seconds** — labelled as a preview, never as the song |

### The shape that keeps both affordances

The out-link is worth keeping. It is the only way to reach the artist's page on
that service, and for Mixcloud the embed licence requires a click-through to
mixcloud.com — though note that requirement is satisfied by the *widget itself*,
which carries the logo, so the badge link is a convenience rather than a
compliance point. Stating that precisely because it would be easy to over-claim.

So split the pill rather than repurposing it: the label plays, the `↗` still
opens. Two targets, one control, no affordance lost. The badges are already
`opacity-0` until `group-hover`, so there is room to widen them on hover without
disturbing the resting row.

### Why this is worth more than a convenience

**It is the manual half of G-16.** A listener on a VPN watches six of twelve chart
songs fail through YouTube while SoundCloud plays them in full. Automatic
cross-source fall-through is the right fix and it is a bigger change; **a source
picker gives the same escape immediately, driven by the person who can see it is
broken.** It also makes the automatic version safer to build later, because the
manual path exercises every `attempt*` function through a real UI first.

**Then persist the choice.** Someone who picks SoundCloud once is usually not
expressing a preference about SoundCloud — they are working around something.
Remembering it per source-pair for the session, or in `localStorage` beside the
other local state, turns one click into a fix for the whole session. That is
G-16's item 3 arrived at from the other direction, and it needs no detection
heuristic at all: the listener has already told you.

### The one thing that had to be got right, and how it was

Whether `sources` on a merged `Song` always carries the fields each attempt
function needs. `byPlayability` sorts them, but a badge renders from
`song.sources` while each attempt function does its own `find` — so a badge for a
source whose `url`/`sourceId` is null would offer to play and then do nothing.

Guarded by construction rather than by remembering: `chosenSource(song, id)`
returns *what `load` would do*, or `null`, and both sides read it. `playbackFrom`
wraps it for the badge and answers `queue` · `manual` · `preview` · `null`; `load`
switches on the same value. The two cannot disagree about whether a source is
playable, because there is only one answer.

## G-18 · Would a signed-in Apple Music subscriber hear the full song? Not before this — now yes

**Built.** `apps/web/app/player/subscription-player.tsx`, plus a `subscription` arm on
`chosenSource` and an `attemptSubscription` beside `attemptSpotify`. Verified in
the running app — see the end of this entry. The analysis below is what it was
before, kept because the trade-off is the part worth re-reading.

Asked directly, and the answer splits in two.

### Today: no, and not for a reason signing in could fix

Timbre does not embed Apple's player. `apple.ts` maps the iTunes Search API's
`previewUrl` — *"a thirty-second clip the Search API publishes for exactly this
purpose"* — and the app plays that URL in **its own `<audio>` element**. It is a
static `.m4a` on Apple's CDN, `audio/x-m4p`, ~1 MB, and it is thirty seconds long
as a file.

Apple never sees a session, an account, or a request it could personalise. There
is nothing to be signed into. Deezer is identical: `preview`, a 30-second MP3 on
`cdnt-preview.dzcdn.net`. **Both are files, not players**, which is exactly why
they can be the last rung of a fall-through ladder — they auto-play and
auto-advance like any other queue member, they just stop at 0:30.

### If it embedded Apple's own player instead: yes

Apple's Marketing Tools documentation is explicit. A listener **not** signed in
gets a 30-second clip; a signed-in Apple Music **subscriber hears full tracks
without leaving the site**, and the embed carries its own sign-in flow.

Measured, and it is constructible today:

```
GET embed.music.apple.com/us/song/1640463908
  200 · no X-Frame-Options · CSP has no frame-ancestors  -> embeddable
GET widget.deezer.com/widget/dark/track/908604612
  200 · no X-Frame-Options · no CSP at all               -> embeddable

and the ids are already in the payload — one search for "boston stella lefty":
  apple  sourceId 1884403093   previewUrl yes
  deezer sourceId 3895241341   previewUrl yes
```

So `embed.music.apple.com/us/song/{sourceId}` needs **no new lookup, no key and
no developer account.** It is the same free-embed shape as Spotify.

### The cost, and it is the same cost Spotify has

**It would be `playback: "manual"`.** There is no documented `postMessage` API for
driving `embed.music.apple.com` from the parent page. MusicKit JS *can* control
playback — `setQueue`, `data-apple-music-play` — but that is a **first-party**
library requiring a signed developer token from a paid Apple Developer
membership, which is the standing non-goal `BLOCKED.md` already records for the
Apple Music API proper.

So the embed can be shown and pressed, and cannot be started by script or
auto-advanced from. `types.ts` already has the tier and `player-context.tsx`
already has `attemptSpotify` as the pattern.

### Therefore it is a second rung, not a replacement

The two things are good at opposite ends and swapping one for the other loses
something either way:

| | preview file (today) | Apple embed |
| :--- | :--- | :--- |
| Length | 30 seconds | **full, for signed-in subscribers** |
| Starts by script | **yes** | no |
| Auto-advances the queue | **yes** | no |
| Needs an account | no | yes, and a paid one |

**Keep the preview as the ladder's floor** — it is the only rung that works for
someone with no subscription at all, which is the audience the README names. Add
the embed **beside** it, the way Spotify's panel already sits beside the queue:
the badge that today says `Apple 30s` could offer both, and say which is which.

**One honest note on who benefits.** A signed-in Apple Music subscriber is, by
definition, someone already paying for streaming — not the reader the README is
written for. That does not make it worthless: plenty of people hold one
subscription and use Timbre for everything outside it, and this is exactly the
case where Timbre would let them hear the whole song rather than a clip. It is
just not a gap in the core promise, and should not be prioritised as though it
were.

**Deezer's widget renders, but the subscriber half is *not* verified.** Measured:
`widget.deezer.com/widget/dark/track/{id}` returns `200`, sends no
`X-Frame-Options` and no CSP, and renders title, artist, a *Play* control and a
link back to deezer.com. Whether a Deezer Premium session in the same browser
yields full-length playback is reasoned from the Apple parallel, **not measured** —
nobody here has an account. Apple's half is documented by Apple; Deezer's is an
assumption, and the label says "if you're signed in" rather than promising.

**One trap, and it cost a test run.** The bare path works and adding query
parameters does not: `…/track/908604612` rendered the player, while
`…/track/908604612?tracklist=false&radius=true` rendered an empty widget in the
same browser a second later.

**A second rung, not a replacement — exactly as the table above argues.**

## G-19 · SoundCloud silently refuses some tracks, and Timbre never noticed — with a correction to my own attribution

**Attribution corrected 15:55.** This entry first blamed the VPN, by analogy with
G-16. That was reaching: the observation — ad-supported tracks refuse,
non-monetised ones play — is measured and holds, but the *cause* is better
explained by a per-track SoundCloud permission than by the network, and I had no
evidence for the network. SoundCloud's own tracker carries the same symptom
against the Widget API, and their help pages document an **Enable app playback**
setting that leaves a track playable on soundcloud.com and through their embeds
while refusing apps that drive it through the API. That would affect every
listener, not only one behind a VPN. Read the fix below rather than the network
theory.

**G-16 says "only one source breaks" and that every non-YouTube source is
untouched by the VPN. That is wrong, and the error was in the method: it checked
whether the SoundCloud Widget could *read* a track, not whether audio flowed.**

Reported as "I still can't play from SoundCloud." Chased as a regression from the
source-picker work; it is not one.

### It is not the badge change

The same construction `soundcloud-player.tsx` uses — an imperative iframe with
`auto_play=true`, `SC.Widget(host)`, `play()` on `READY` — reproduces the symptom
on a bare page with Timbre entirely out of the picture:

```
events: READY, called play(), PAUSE, PLAY, PAUSE, PAUSE
state : {"position": 0, "paused": true}
```

And in the app the widget is holding the right track: asked directly,
`getCurrentSound` returns `{"title":"Boston","duration":170905}` — 2:50, matching
the transport. Metadata is fine. Nothing is misrouted.

### What it actually is

The discriminator is `monetization_model`, and it is the same wall as G-3a and
G-16 — one layer further down. Same browser, same minute:

```
soundcloud.com/lofi-beats-1/tu-hi-haqeeqat-…   BLACKBOX       pos 1782 ms, paused false, 64 progress ticks
soundcloud.com/deedecollective/lofi-alt…      BLACKBOX       pos 0, paused false (buffering)
soundcloud.com/stellalefty/boston             AD_SUPPORTED   pos 0, paused TRUE, 0 ticks
```

**A non-monetised upload plays and advances. The ad-supported one goes straight
to paused at zero.** That rules out the obvious alternative — a headless browser
with no audio device would have failed all three.

Asking for the audio directly says the same thing. The track reports
`policy: MONETIZE`, `monetization_model: AD_SUPPORTED`, `snipped: false`, and
eight transcodings — and the stream-authorize endpoint, with a valid
`client_id` *and* the track's own `track_authorization`, answers:

```
GET …/media/…/stream/progressive?client_id=…&track_authorization=eyJ0eXAiOiJKV1Qi…
  404 {}
```

Metadata is entitled; audio is not.

### What this corrects, and what survives

**G-16's table is right about what it measured and wrong about what it
concluded.** `policy=MONETIZE, duration=233759, streamable=true` was a *metadata*
read through `getCurrentSound`. It says the credential may see the track. It says
nothing about whether the CDN will serve bytes to this network, and the answer is
that it will not for the licensed catalogue.

So the corrected picture, all measured from the same VPN exit:

| | metadata | audio |
| :--- | :--- | :--- |
| YouTube, label uploads | fine | **barred** (6/12 songs, every candidate) |
| SoundCloud, `AD_SUPPORTED` | fine | **barred** (pauses at 0) |
| SoundCloud, non-monetised | fine | **plays** |
| Audius | fine | **plays** (`206`, `audio/mpeg`, bytes fetched) |
| Deezer / iTunes 30s previews | fine | **plays** (`206`, bytes fetched) |

The three that still work are the three where I fetched actual bytes rather than
asking a player what it thought. **That is the lesson worth keeping: for a
playback question, a metadata field is not evidence. Fetch the audio, or watch
the position advance.**

**G-16's recommendation survives, narrowed.** Cross-source fall-through is still
the right fix, and the ladder can still leave YouTube — but SoundCloud is not the
rescue for a *chart* song under a VPN, because the same rights layer catches it.
What rescues those is Audius (for what it carries) and the 30-second preview,
which is why `57af890` matters more than it looked. The picker from G-17 is also
still useful, for the opposite reason: it lets someone reach the non-monetised
upload that *does* play.

### Fixed: the silent stall now reports itself

The defect that is *Timbre's* is not the refusal — it is that nothing noticed.
Measured: the widget emits `READY → PAUSE → PLAY → PAUSE → PAUSE` and **no
`ERROR` event ever fires**, so the `ERROR` binding in `soundcloud-player.tsx`
never runs, `handleError` is never called, and the reader watches `0:00 / 2:50`
for ever with a play button that does nothing.

`soundcloud-player.tsx` now arms a seven-second watchdog after it calls `play()`.
If the widget is still paused at position 0 when it fires, that is reported as a
refusal with a stated reason. `PLAY_PROGRESS` cancels it — real progress is the
only honest proof it started, since `PLAY` alone fires even on a track that
immediately re-pauses.

**One trap, hit while writing it.** The first version passed
`worthRetrying: true`, reasoning that the ladder should fall through. It must be
`false`: `handleError`'s ladder ends with
`if (soundcloud) attemptSoundCloud(soundcloud)`, guarded *only* by the contract
its own comment states — "SoundCloud … reports not-worth-retrying, so a failure
exits above rather than looping back here." Reporting `true` walked the ladder
straight back into the same stalled track, for ever, and the symptom was
indistinguishable from the bug being fixed.

Verified in the app against `soundcloud.com/stellalefty/boston`: at ~16 s
(READY is slow, then seven seconds) the transport reads *"SoundCloud wouldn't
start this track — the uploader may not allow playback outside soundcloud.com.
Try another source from the badges."* `lint`, `typecheck` and `pnpm test` clean.

### For whoever hits this next

The signature is precise and worth recognising: **the track loads, the title and
full duration appear, the transport shows `0:00 / 2:50`, and the play button
never turns into a pause button.** That is not a broken player and not a broken
Timbre. It is the network being refused the audio, and the tell is that
independent uploads on the same service play normally.

## G-20 · Spotify's 30-second preview — the embed can never fix it, and what can

Asked to keep looking for a way around it. There is one, it is not the embed, and the embed
route is now closed by measurement rather than by guess.

### Why the embed serves a clip, precisely

Not Premium. The embed decides what to serve by reading the listener's Spotify session, and
being an iframe on `open.spotify.com` inside somebody else's page, it reads it through
**third-party cookies**. Chrome blocks those by default, the embed sees no session, and it
serves 30 seconds — to Premium subscribers exactly as readily as to anyone else. Spotify's
own developer forum carries this as an open complaint.

### Both ways of granting storage access are closed

- **`document.requestStorageAccessFor()`** — the API built for precisely this shape, a
  top-level site asking on behalf of an embed — is **Related Website Sets only** in Chrome.
  Timbre and Spotify are not in a set and cannot be.
- **`allow="storage-access"` on the iframe**, letting Spotify's own frame ask, fails twice
  over. First, `createController` **replaces** any element it is given: passing a pre-built
  `<iframe>` carrying the attribute produced a Spotify-built iframe with
  `allow="autoplay; clipboard-write; encrypted-media; fullscreen; picture-in-picture"` and no
  `storage-access`. Second, and decisively, **Spotify's embed does not implement the API at
  all** — 1 751 KB of its JavaScript across 15 bundles was scanned:

  ```
  requestStorageAccess   0
  hasStorageAccess       0
  storage-access         0
  ```

  So even if the attribute could be attached, nothing inside the frame would ever call it.

**The embed is therefore a dead end for full playback**, permanently and by construction, not
by configuration. The only thing that changes it is the listener allowing third-party cookies
for `spotify.com` in their own browser, which is their setting and not something the app can
reach.

### The mechanism, so nobody re-derives it

The embed page server-renders its own auth state into `__NEXT_DATA__` before any script runs:

```
accessToken   BQBXqb6l53L8vLxmzAGp3DEf…      (anonymous)
isAnonymous   true
clientId · accessTokenExpirationTimestampMs
```

**`isAnonymous` is decided on Spotify's server from the cookies on the iframe request**, and
the token is minted at that moment. No cookie, anonymous token, preview — settled before the
player exists. `isAnonymous` appears 23 more times across the bundles, so it is the switch the
whole embed reads.

That is why nothing client-side works, and it is worth stating as the general fact rather
than as a list of failed attempts: **the decision is made server-side, from a cookie, before
Timbre's page has any contact with the document.** An iframe attribute cannot change it, a
header cannot, and injecting into a cross-origin document is not possible.

### Without a developer account, the two things that do work

Both are already in the app, and neither is a workaround:

1. **The listener allows third-party cookies for `spotify.com`.** The same embed then arrives
   with a session, mints a *user* token, and plays full length. This is the supported path,
   not a trick — which is why the notice under the player names that exact setting rather
   than saying something vague about availability.
2. **The `↗` on the Spotify badge.** A tab on `open.spotify.com` is a first-party context, so
   the listener's cookies apply and the track plays whole. Already there since the badges
   were built.

### The route that does work in-app, and it is already half-written in this repo

**The Web Playback SDK** (`https://sdk.scdn.co/spotify-player.js`) does not use cookies at
all. It runs **first-party in Timbre's own page** and authenticates with a bearer token:

```js
const player = new Spotify.Player({
  name: "Timbre",
  getOAuthToken: (cb) => { cb(token); },
  volume: 0.5,
});
```

It registers a playback device on the listener's account and plays **full tracks**. The
cookie problem simply does not arise, because there is no cross-site cookie in the design.

**And the token it needs is the one `SEARCH-ROUTES.md` R3 already describes.** That entry
works through Authorization Code + PKCE — no client secret, safe in a browser — and concludes
*"viable for a personal or self-hosted build, never for a hosted one"* because Development
Mode caps an app at five users. That is right, and it was written about **search**. Nobody
connected it to playback: the same token is the only route to a full-length Spotify track in
this app. For a personal or self-hosted deployment, five seats is not a limitation at all.

### What it costs, stated plainly

- **A registered Spotify app.** Free, but since Feb 2026 the owner must hold Premium —
  `BLOCKED.md` records that — which collides with the standing no-developer-accounts non-goal.
- **Five users**, and that is a property of the app rather than the deployment, so it cannot
  be grown by self-hosting more copies.
- **The listener must be Premium.** Spotify's documentation is explicit: *"The Web Playback
  SDK requires a Spotify Premium subscription (mobile only types of premium subscriptions are
  excluded)."*
- **Non-commercial only.** *"This SDK must not be used in commercial projects without
  Spotify's prior written approval."* Compatible with where Timbre is, and it hard-binds
  `EXPOSURE.md` **E-1**'s open question about donations.
- **§IV.2 is more engaged, not less.** The embed at least kept Spotify's audio inside
  Spotify's own player. The SDK plays Spotify audio **through Timbre's player**, in a queue
  alongside YouTube and SoundCloud. That is much closer to the blending the clause is about
  than anything discussed so far — closer even than the autoplay change in G-19's neighbour.

### The recommendation

**Do not build it on the strength of "there should be a way".** There is a way, and its price
is a developer account, a Premium subscription, a five-user ceiling and the clearest §IV.2
exposure in the project. Every one of those is a standing non-goal or an open question
somewhere in `docs/`.

What is worth doing regardless, and is already done: **say why the clip is a clip.** The
player now detects a ~30s duration on a track known to be longer and names the cause and the
setting. That converts a mystery into a two-click fix the listener can perform, and it costs
nothing.
